<objective>
Harden the post-release hydration-race guard introduced in quick-260518-j5j by adding an `ignoreItemId` option alongside the existing `ignoreReservationId`. The user retested j5j and reported the bug persists because `hydrateActiveReservation` is returning an active reservation with a DIFFERENT reservationId for the same item — a stale-active row (likely accumulated from emulator restarts that lost the setTimeout auto-expiry per iux/pdp scenarios). The exact-reservationId guard cannot catch this; an item-scoped guard can.

After this plan, the suppression check fires when EITHER the returned reservationId matches OR the returned itemId matches the just-released item. The user can clean their DB in parallel; this hardening also benefits production users with similar accumulated state (Cloud Tasks failures, manual DB drift, etc.).

Purpose: Make the post-release UI deterministic on RegistryPage regardless of stale-active row presence on the same item.
