- Total canvas: 108dp × 108dp
- Visible/clip mask area: inner 72dp × 72dp circle (centered)

- ⇒ Two-line text "gift" / "maison." MUST fit within the 72dp safe circle, with text width ≤ ~80% of safe-zone width (so it survives all launcher mask shapes — circle, squircle, rounded square, teardrop).

<pitfalls>
- **Fontconfig discovery on macOS:** `rsvg-convert` reads fonts via fontconfig. The bundled `instrument_serif_italic.ttf` is in `res/font/` (Android resource dir) and is NOT visible to fontconfig. Solution: copy it to `~/Library/Fonts/InstrumentSerif-Italic.ttf` (user-level macOS font install — no admin needed, persists, fontconfig auto-discovers). After copying, run `fc-cache -f` (optional but speeds up first lookup). Verify with `fc-list | grep -i instrument` before rasterizing.
- **Round launcher clipping:** Even with safe-zone math, the trailing accent `.` can land outside the safe circle if "maison." is rendered too wide and the period sits at the rightmost edge. Mitigation: include the `.` in the text-width measurement and shrink font-size until "maison." (period included) is ≤ 80% of safe-zone diameter.
- **SVG → bitmap antialiasing:** Use `rsvg-convert --background-color=#F7F2E9` so the paper background is baked into the legacy PNGs (no transparency). Adaptive-icon XML supplies the background separately and ignores transparency in the foreground SVG outside the safe zone, but legacy PNG users see the full square — and a transparent square reads as black on most launchers.
- **`drawable-anydpi-v24` for foreground:** Vector drawables are supported from API 21 but `<path>` only — no `<text>` node in Android vector format. The foreground MUST be either (a) a rasterized PNG copied into `drawable-*dpi/` (loses density flexibility), or (b) the SVG converted to Android `<vector>` with text outlines as `<path>` elements (heavy, brittle), or (c) **THIS PLAN'S CHOICE**: ship a high-density PNG at `drawable-xxxhdpi/ic_launcher_foreground.png` (432×432px) so adaptive launchers get crisp text, AND ship legacy bitmap PNGs in `mipmap-*` for pre-API-26 devices. We do NOT need a `<vector>` XML for the foreground if we use a PNG — simpler and visually identical.
  - ⇒ REVISED file list: foreground is `drawable-xxxhdpi/ic_launcher_foreground.png` (NOT an XML vector). Task 2 wires the adaptive-icon XML to this PNG.
- **No `android:icon` in current manifest:** This is a NET-NEW addition. Make sure to add BOTH `android:icon` and `android:roundIcon` on the `<application>` element. Without `android:roundIcon`, Pixel launchers (and others that request the round variant explicitly on API <26) fall back to the system stub.
- **Themed icons (Android 13+):** OUT OF SCOPE for this quick task. Adding a `<monochrome>` layer requires a single-color silhouette PNG and a `mipmap-anydpi-v33/ic_launcher.xml`. User asked for "adaptive icon (foreground + background) with legacy fallbacks" — themed icons are an opt-in beyond that. Mention in summary as a future polish.
- **`mipmap` vs `drawable` for the foreground PNG:** Android Studio's New > Image Asset wizard puts `ic_launcher_foreground` in `mipmap-*` by default in modern templates, but `drawable-*` is equally valid and reduces APK size (mipmap PNGs are kept across densities; drawable PNGs are stripped per-device). For a foreground that's already a single high-density PNG, `drawable-xxxhdpi` is cleaner. The adaptive-icon XML references it as `@drawable/ic_launcher_foreground` regardless.
</pitfalls>
