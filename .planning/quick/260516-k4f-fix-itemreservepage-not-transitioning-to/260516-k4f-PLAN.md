<objective>
Fix ItemReservePage failing to transition into the reserved-by-me detail after a successful Reserve from the BROWSE_AVAILABLE branch. The root cause is a two-hook split: `useReservationForItem` (used to read `active` for render decisions) fetches via the `getReservationForItem` callable and NEVER observes the shared `useActiveReservation` React context; meanwhile the Reserve mutation's onSuccess (ItemReservePage.tsx:101-118) only seeds the shared context. After Reserve, `lookupActive` from `useReservationForItem` stays null, the page reads `active === null`, falls into the !active branches, and once the Firestore item.status flips to 'reserved' the page renders BROWSE_RESERVED_BY_OTHER for the user's OWN just-made reservation.

**Fix shape:** rename the destructured `active` from `useReservationForItem` to `lookupActive`; pull `active: sharedActive` from `useActiveReservation`; derive a new `const active = (sharedActive && sharedActive.itemId === itemId) ? sharedActive : lookupActive` immediately after both hooks. The new `const active` shadows at the SAME scope as the old destructured one, so every existing downstream reference (`useCountdown(active?.expiresAtMs)`, the sawNonExpiredRef tracking effect, the navigate-on-status-flip effect, `effectiveActive` derivation, branches 4/5, `renderReservedByMeDetail({ active: effectiveActive })`) compiles and behaves correctly with zero textual edits. The iux-introduced `effectiveActive` gate continues to wrap the derived `active` unchanged.

**Constraints (re-stated from spec):**
- Client-side only. NO backend changes, NO i18n changes, NO new components/hooks/files.
- 167/167 pre-existing web tests stay GREEN.
- D-06 unchanged (no reserver/giver name surfaced).
- The fix touches ONLY ItemReservePage.tsx — useReservationForItem.ts, useActiveReservation.ts, useCreateReservation.ts are NOT modified.
- The derived `active` line is the ONLY new computation — the rest of the file change is rename + comment cleanup + JSDoc update.
- effectiveActive (from iux) keeps wrapping the derived `active`, so stale-expired-on-mount short-circuiting still works for shared-context-sourced actives in the rare case where a user drifts past 30 minutes while staying on the page. K-09 (regression guard for in-session expiration) continues to pass because sawNonExpiredRef flips true on the first non-expired observation regardless of whether the active came from sharedActive or lookupActive.

Purpose: restore the k37 BROWSE_AVAILABLE → Reserve happy path. Without this fix, a user signed in (or guest with stored identity) who clicks Reserve from the available-state detail page sees their own reservation as "Already reserved by another guest" instead of getting the countdown + Release + Confirm CTAs. This is the SAME UX bug we shipped k37 to fix in the first place — just one level deeper in the flow.
