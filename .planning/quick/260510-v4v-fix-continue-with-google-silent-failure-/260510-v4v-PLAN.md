**4c. Replace the two empty catch blocks** (currently lines 130-134) with the full four-catch chain. The replacement MUST live inside the same `scope.launch { try { ... } }` block that already wraps the Credential Manager call. Replace lines 130-134 with:

```kotlin
                    } catch (e: GetCredentialCancellationException) {
                        // User dismissed the Credential Manager sheet — silent no-op (no log, no toast).
                        // Dismissal is intentional; surfacing an error here would be noise.
                    } catch (e: GetCredentialException) {
                        Log.w(TAG, "Continue with Google failed: ${e::class.simpleName} — ${e.message}", e)
                        viewModel.setError(context.getString(R.string.auth_error_google_signin_failed))
                    } catch (e: CancellationException) {
                        // Coroutine was cancelled (e.g. composition torn down). Re-throw to preserve
                        // structured concurrency — never swallow CancellationException.
                        throw e
                    } catch (e: Exception) {
                        Log.w(TAG, "Continue with Google unexpected error: ${e::class.simpleName} — ${e.message}", e)
                        viewModel.setError(context.getString(R.string.auth_error_google_signin_failed))
                    }
```

CRITICAL ordering rules (Kotlin catches top-down — wrong order = wrong handler runs):
1. `GetCredentialCancellationException` MUST be first — it's a subclass of `GetCredentialException`, so the generic catch would otherwise swallow it and we'd toast on user dismissal.
2. `GetCredentialException` second — catches the rest of the Credential Manager failure family (NoCredentialException, etc.). The `e::class.simpleName` in the log line distinguishes them for diagnosis.
3. `CancellationException` (kotlinx) third — re-throw is mandatory; if we catch it in the generic Exception below and toast, structured concurrency breaks.
4. `Exception` last — safety net for FirebaseAuth rejections inside `viewModel.signInWithGoogle()` and any other unexpected failure. Same user-facing message; the log distinguishes.

Do NOT change the try block contents or any other code in the GoogleBanner onClick. The only changes are: the catch chain replacement, the three new imports, and the TAG constant.

**WHY this shape (so executor doesn't second-guess):**
- We use `Log.w` (warn) not `Log.e` (error): user-facing failure recovery, not assertion failure.
- We log `e::class.simpleName` separately because logcat's stacktrace is verbose and the user/dev needs the class name at a glance.
- Same user-facing string for both error catches because the user can't act differently on "no credentials" vs "FirebaseAuth rejected" — but the log differentiates for the dev.
- We do NOT touch `viewModel.signInWithGoogle` itself — its internal failures already propagate via its own `result.fold(onFailure = ...)` path (AuthViewModel.kt lines 137-142). If FirebaseAuth rejects inside that coroutine, the existing path sets errorMessage; if it throws synchronously somehow, our generic catch picks it up.
