<diagnosis>
Two parallel races on RegistryPage re-mount after release-from-ItemReservePage:

A. **Hydration race (DOMINANT — explains why Web Inspector open masks the bug):**
   - User clicks Release on ItemReservePage → backend transactionally flips reservation to status='expired' and item.status to 'available'.
   - Release-success useEffect fires → oiy optimistically patches the items cache → navigate(`/registry/:id`) → RegistryPage RE-MOUNTS.
   - RegistryPage's useActiveReservationHydration effect fires immediately on mount (line 42) — its conditions are met (registryId, authReady, user OR identity, active===null since clearActiveReservation just ran).
   - Hydration callable `hydrateActiveReservation` queries Firestore for reservations where `giverId == auth.uid` (or `giverEmail == X && giverId == null` for guests) AND `status == 'active'` AND `registryId == X`. Composite index propagation lags by ~ms — the just-flipped 'expired' reservation may briefly STILL match the index on the `status == 'active'` filter.
   - If the callable returns the just-released reservation, `set(r.data.active)` re-populates the shared ActiveReservationContext → StickyReserveBanner becomes visible (line 206) → ReserveDetailSection becomes visible (line 209) → for ~hundreds of ms until either the next hydration re-fire (rare — gated by lastKeyRef) OR the user navigates away.
   - Web Inspector open SLOWS callable round-trip enough that the index catches up before the response — explains the masking behavior.

   **j5j fix:** Pass `recentReleasedReservationId` via navigate state. Hydration hook gets a new optional `{ ignoreReservationId }` 2nd arg. After callable resolves, if the returned active matches the ignored ID, treat as null (setStatus 'empty', skip set). Surgically scoped — the hook still hydrates legitimately on refresh/cold-start.

B. **Snapshot race (SECONDARY — supplements oiy):**
   - oiy patches the React Query cache via `setQueryData(['registry', :id, 'items'], updater)` BEFORE navigate. The destination RegistryPage's first render reads the patched cache → item shows 'available'. Good.
   - But: useItemsQuery on RegistryPage re-mount sets up a fresh `onSnapshot` listener. Firestore client SDK fires the first snapshot from local cache IMMEDIATELY (sync or near-sync) BEFORE the server roundtrip — this is Firestore's normal latency-compensation behavior. The local cache (different from React Query's cache) may still hold the stale `item.status='reserved'` doc.
   - That first snapshot callback at useItemsQuery.ts line 21 does `queryClient.setQueryData<Item[]>(queryKey, items)` — OVERWRITING oiy's optimistic patch with stale data. Tile briefly flashes RESERVED.
   - ~50-500ms later the server snapshot fires with fresh `status='available'` data and the tile settles correctly.

   **j5j fix:** itemsForRender useMemo on RegistryPage overrides the just-released item to 'available' regardless of what useItemsQuery returns — for the lifetime of this mount when location.state.recentReleasedItemId is set. Since the override is computed downstream of useItemsQuery and consumed by ItemGrid + counts, the tile NEVER renders 'reserved' even if the cache briefly contains stale data. Once the user navigates away or the cache fully syncs, future mounts don't carry the state and the override is a no-op.

Why navigate state (and not Context, useRef, sessionStorage, etc.)?
- **One-shot semantics:** location.state is naturally scoped to a single navigation. Refresh clears it. Navigate-away-and-back without state clears it. No cleanup logic needed.
- **No global mutation:** doesn't pollute Context, doesn't require a top-level provider, doesn't risk leaking into unrelated routes.
- **Type-safe and observable in tests:** MemoryRouter's `initialEntries` accepts state, mockNavigate can be inspected for the state arg.

Why useLocation read at top of component (NOT in useEffect)?
- React Router guarantees `useLocation()` returns the location for the CURRENT match. `location.state` is a plain JS value (whatever was passed to navigate); reading it during render is correct and gives a stable value across re-renders within the same mount. Reading it in an effect would introduce a tick of delay — the FIRST render must already see the override or there's still a flash window.

Why itemsForRender as a memo (NOT modifying useItemsQuery)?
- useItemsQuery is shared across pages, tested independently, and snapshot-listener-backed. Mutating it would couple it to the j5j use case and risk breaking other consumers. The memo is a local render-shape transform — same data, different shape — entirely owned by RegistryPage.
- Returning the original `itemsQ.data` when no override applies preserves referential identity for downstream useMemo/React.memo optimizations (e.g. ItemGrid is likely memoized).

Why update counts memo input?
- ProgressStrip + FilterChips display counts derived from the items list. If counts read raw `itemsQ.data` while ItemGrid reads `itemsForRender`, the strip would briefly show "1 reserved" while the grid shows zero reserved items — visually contradictory. Counts MUST consume the same source as the grid.

Edge cases:
- itemsQ.data === undefined (loading): itemsForRender === undefined. No override fires; existing skeleton render path takes over. SAFE.
- recentReleasedItemId is set but the item is NOT in the cache (deleted by owner during the user's reserve session): `.find(i => i.id === recentReleasedItemId)` returns undefined → no override entry to write → array returned unchanged. SAFE.
- recentReleasedItemId is set AND the item is already 'available' (oiy patch landed, snapshot already synced): the conditional `if (item.status === 'reserved')` is false → override is a no-op identity → original array returned by reference. SAFE.
- recentReleasedItemId is set AND the item is 'purchased' (some other giver bought it in the meantime, snapshot fired while user was on ItemReservePage): conditional false → no override → user sees 'purchased' status correctly. SAFE — does NOT downgrade.
