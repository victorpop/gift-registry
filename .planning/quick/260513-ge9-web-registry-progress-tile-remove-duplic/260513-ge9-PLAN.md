<objective>
Two related fixes to the PROGRESS tile on the web registry detail page (/registry/:id):

(1) **Remove the duplicate count.** Current rendering shows "2 2 of 3 chosen" because the body line ALSO interpolates the chosen count via `{{n}}`. Drop the `{{n}}` from the i18n template so the body becomes "of {{total}} chosen" — the large numeral remains the sole source of the count.

(2) **Hide the Share CTA for non-owners.** Today the "Share this registry" button is rendered unconditionally; gift givers (non-owners, including unauthenticated guests) should not see it. Owners keep it.

Purpose: The duplicate "2 2" rendering is a visible bug that erodes trust in the registry's polish, and the Share CTA on the giver experience is functionally pointless (a giver sharing the link to themselves is meaningless) and visually noisy.

Output: Updated i18n copy (4 files — mirror convention), a small prop addition to ProgressStrip, a one-line isOwner computation in RegistryPage, and a small vitest spec locking the new behavior.

Investigation outcome (from codebase reading, NOT a future TODO):
- The bug source is `web/src/features/registry/ProgressStrip.tsx` lines 30–35: a `<span>` renders `{totalChosen}` as the big numeral, and the very next `<span>` calls `t('web_hero.progress_copy', { n: totalChosen, total })` — but `progress_copy` is `"{{n}} of {{total}} chosen"` (EN) / `"{{n}} din {{total}} alese"` (RO). The `{{n}}` is the duplicate. → Fix: drop `{{n}}` from BOTH copies AND remove `n: totalChosen` from the t() call.
- Owner detection: web does NOT yet have a dedicated `isOwner` helper, but the inputs are trivially available — `useAuth()` (web/src/features/auth/useAuth.ts) returns `{ user }` where `user.uid` is the Firebase UID, and `registryQ.data?.ownerId` is the canonical owner field on the Registry type (web/src/lib/firestore-mapping.ts:9, mapped from the Firestore doc on line 32). `RegistryPage.tsx:33` already destructures `useAuth()` for the auto-reserve flow, so we just reuse `user`. → Compute `const isOwner = !!user && registryQ.data?.ownerId === user.uid` after `total`/`totalChosen` are derived (after line 189), and pass to `<ProgressStrip />` at line 225.
- Guest givers (unauthenticated, `user === null`) correctly fall through to `isOwner === false` and lose the Share button — matches the requirement.
- No existing pattern named `isOwner` exists on web, so we introduce one locally inline in RegistryPage. NOT extracting into a hook — it's a one-liner used in exactly one place. (Android's `isOwner` pattern from 260507-uzv/veb/vrp lives in Kotlin and does not apply here.)
- i18n duplicate paths: `web/src/i18n/{en,ro}.json` is the runtime source loaded by Vite; `web/i18n/{en,ro}.json` is the legacy mirror retained for tooling/parity per the convention established in quick-260512-vlg and quick-260513-fnm. Both must be edited in lockstep.
- No existing test covers ProgressStrip — adding a focused spec (no RegistryPage integration test changes needed; the existing RegistryPage.test.tsx already mocks useAuth to `user: null` and doesn't assert on Share visibility, so it stays green).
</objective>
