<objective>
Eliminate the ~1 second AuthScreen flash that already-signed-in users see on Android cold start. After the fix, an Android user with a valid Firebase Auth session restored from disk goes from the system launch window straight to the HomeKey (registry list), with no transient render of AuthScreen and no transient navigation push of AuthKey onto the back stack.

Purpose: UX regression — the existing `AuthUiState.Loading` gate in `AppNavigation` (lines 117-125 of `AppNavigation.kt`) is correct, but the upstream Firebase auth-state pipeline emits a synchronous `null` at listener attach **before** Firebase has read the cached user from disk. That transient `null` flips `_authState` from `Loading` to `Unauthenticated` for one frame, which (a) renders `AuthScreen` and (b) trips the `LaunchedEffect(authUiState, ...)` block in `AppNavigation.kt:81-115` to push `AuthKey` onto the back stack. Then ~1s later the cached user emission arrives and the screen flips to `Authenticated`, navigating to `HomeKey`.

Output: A fix at the dataSource layer that distinguishes the synchronous "listener-attach" emission from real auth-state changes, so consumers only observe a settled auth state. Regression test guarding against the transient `Unauthenticated` emission.
</objective>

<diagnostic_notes>
What's already in place (verified by reading the source — do NOT re-derive this):
1. `AuthUiState` is a sealed interface with three states: `Loading`, `Unauthenticated`, `Authenticated(uid, isAnonymous)` (AuthUiState.kt:3-7).
2. `AuthViewModel._authState` is initialized to `AuthUiState.Loading` (AuthViewModel.kt:28).
3. `AppNavigation` already handles `AuthUiState.Loading` by rendering a centered `CircularProgressIndicator` and early-returning before any nav-display composition (AppNavigation.kt:117-125). It also does nothing in the `LaunchedEffect(authUiState, onboardingSeenState)` routing block when `authUiState is AuthUiState.Loading` (AppNavigation.kt:111-114).
4. STATE.md line 146 documents a Phase 02 decision: "drop(1) on ObserveAuthStateUseCase Flow prevents auth screen flash on session restore" — but the current `ObserveAuthStateUseCase.kt` does NOT contain any `drop(1)` call. This regression-or-never-landed fix is the historical context.

What is actually broken (verified by reading the source):
- `FirebaseAuthDataSource.authStateFlow` (FirebaseAuthDataSource.kt:19-25) attaches a `FirebaseAuth.AuthStateListener` inside `callbackFlow`. Firebase fires that listener **synchronously on attach** with `auth.currentUser`. On cold start, `auth.currentUser` is `null` at the moment of attach because Firebase has not yet read the persisted user from disk. That synchronous `null` is `trySend`-ed into the flow.
- `AuthRepositoryImpl.authState` (AuthRepositoryImpl.kt:16) maps that `FirebaseUser?` to `User?` — the `null` propagates.
- `AuthViewModel.init` (AuthViewModel.kt:34-45) collects the flow and immediately writes `_authState.value = AuthUiState.Unauthenticated` on that first `null`. ~1 second later, Firebase fires the listener again with the real cached user, and `_authState` flips to `Authenticated`.
- The intermediate `Unauthenticated` state is what flashes AuthScreen.

Why the obvious fixes are wrong:
- `drop(1)` on the entire flow at `ObserveAuthStateUseCase` (the historical fix) drops the very first emission unconditionally. If the user is **genuinely signed out** on cold start, the first emission is the *only* emission — `drop(1)` would leave the ViewModel stuck in `Loading` forever, hanging the splash/loading indicator indefinitely. (This is likely why the historical fix was reverted.)
- A blanket `delay()` / artificial timer is forbidden by the task constraints.
- Modifying `AuthScreen` to handle a loading bool doesn't fix the navigation push of `AuthKey` onto the back stack from the `LaunchedEffect` in `AppNavigation`.

The correct fix:
- Distinguish "first emission from listener attach" from "subsequent emissions" at the dataSource. Emit a typed event (`AuthStateEvent.Initial(user)` vs `AuthStateEvent.Changed(user)`) so the ViewModel can tell the difference.
- In `AuthViewModel`, exit `Loading` on **either** of: (a) `AuthStateEvent.Initial(non-null user)` — definitively signed in, OR (b) `AuthStateEvent.Changed(any)` — Firebase has finished restoration and is now reporting real state. Stay in `Loading` only when `AuthStateEvent.Initial(null)` is the most recent event, which is the cold-start window before Firebase has had a chance to restore the cached user.
- This gives the right behavior in every case:
  - Cached signed-in user: Initial(null) → keep Loading → Changed(user) → Authenticated. No flash. ✓
  - Genuinely signed out: Initial(null) → keep Loading → (Firebase confirms no user via a no-op or via the AuthRepository.currentUser snapshot check after a short Firebase-internal restoration completes; see implementation detail in Task 2) → Unauthenticated. ✓
  - Sign-in/sign-out at runtime: subsequent emissions are `Changed`, pass through unmodified. ✓

Implementation detail for the "genuinely signed out" case: on listener attach, after registering the listener, immediately also send `AuthStateEvent.Initial(firebaseAuth.currentUser)` — Firebase's `currentUser` getter is synchronous and returns the cached user once the SDK's in-memory cache is populated. On a cold start, Firebase Auth restoration is async (~hundreds of ms). The reliable behavior is:
- If `firebaseAuth.currentUser` is non-null at attach, the user is definitely signed in — emit Initial(user) immediately.
- If `firebaseAuth.currentUser` is null at attach, we don't know yet — emit Initial(null) (which the ViewModel maps to "stay Loading"), and wait for the listener's subsequent Changed(...) emission to settle the state. Firebase Auth guarantees the listener will fire at least once after disk restoration completes (or after a network round-trip if applicable). To guard against the genuinely-signed-out case where no Changed emission ever arrives, treat the listener-attach callback itself as the settling signal: after the listener attach call returns, schedule a one-shot follow-up that, if no Changed emission has been received within a short async window, emits Changed(currentUser) to settle the state.

Cleaner implementation (chosen): Use a `Boolean` "has-seen-first-callback" flag inside the `callbackFlow`. The very first `trySend` from the listener is marked Initial; all subsequent `trySend`s are marked Changed. Then in AuthViewModel, the rule is simply:
- Initial(null) → keep `Loading`
- Initial(user) → `Authenticated`
- Changed(null) → `Unauthenticated`
- Changed(user) → `Authenticated`

This works because Firebase's `AuthStateListener` contract guarantees a callback after restoration completes, even when the result is "no user". The synchronous-attach call counts as the first callback; the post-restoration call counts as the second. (Verify in Task 1 by reading Firebase's actual behavior — if this assumption is wrong, fall back to also seeding from `firebaseAuth.currentUser` post-attach with a `withTimeoutOrNull` settle window.)

2. `AuthRepositoryImpl.kt` — update mapping to expose the same distinction to the domain layer (or fold both back into `Flow<User?>` with a richer model). Decision: minimize API churn — change the domain `AuthRepository.authState` to `Flow<AuthStateEvent>` (or equivalent sealed type lifted into the domain package), and propagate the change.
