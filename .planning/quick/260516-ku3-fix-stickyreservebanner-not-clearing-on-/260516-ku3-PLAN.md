<objective>
Fix `StickyReserveBanner` failing to clear the banner on a second release within the same mount. Reproduction: signed-out user reserves item A, reserves item B → shared useActiveReservation now holds B → RegistryPage's StickyReserveBanner shows B → user clicks Release → backend cancels B, toast fires, clear() empties context → useActiveReservationHydration re-resolves to A → banner re-appears with A → user clicks Release on A → backend cancels A, BUT the page does NOT update — banner stays visible until manual refresh.

**Root cause:** `web/src/features/reservation/StickyReserveBanner.tsx` lines 50-67. `releaseSuccessToastedRef` is set to `true` after the first successful release and never reset. The banner stays mounted across releases (unlike `ItemReservePage`, which navigates away on success and unmounts), so on the second release the useEffect's `!releaseSuccessToastedRef.current` guard is false and the entire success branch is skipped — no toast, no `clear()`, banner stays mounted.

The same latent issue applies to `releaseErrorToastedForRef`: it's keyed by error message (works for distinct errors within a single release attempt) but a repeated identical-message error after a success would also be silently dropped.

**Fix shape:** add a single new useEffect immediately BEFORE the existing release-success useEffect (currently at line 61). When `releaseStatus === 'pending'`, reset BOTH refs: `releaseSuccessToastedRef.current = false` and `releaseErrorToastedForRef.current = null`. `useReleaseReservation.release()` calls `setStatus('pending')` at line 33 unconditionally on every release attempt, so pending is a reliable reset signal. Source-order placement (new effect BEFORE success/error effects) is mandatory — see the "Constraints" note below.
